# Intrusion Evidence Capture

## Scope and current implementation

The server-side request evidence collector is implemented as an optional ASGI middleware in `security/ip_evidence.py`. It observes HTTP responses generated by the Neon Shield API and records source IP information for HTTP 401, 403, and 429 responses. It does not scan, probe, exploit, or contact the remote source.

This is not a universal IP grabber. An app cannot reliably discover the public IP address of someone attempting to compromise a user's iPhone or computer unless that activity reaches a service or network sensor that is authorised to observe it. iOS and Android also restrict background network inspection. Device-local compromise telemetry requires separate, platform-specific, permission-compliant integrations and cannot be promised by this server middleware.

## IP provenance and reverse proxies

- The socket peer address is authoritative when the application is directly exposed.
- `X-Forwarded-For` is ignored unless the immediate peer belongs to an explicitly configured trusted proxy CIDR.
- When trusted, the chain is walked from right to left to select the first untrusted hop.
- Never trust forwarded headers from arbitrary clients.
- Configure `trusted_proxy_cidrs` from the actual hosting provider/network topology. Do not guess these ranges.

## Event policy

The middleware records only HTTP 401, 403, and 429 responses. It records UTC timestamp, event type, severity, source IP, IP provenance, destination service domain, HTTP method, status and a bounded user-agent value. It does not record request bodies, passwords, authentication tokens, cookies, message contents, or full URL paths/query strings.

An IP address is an investigative lead, not proof of a person's identity. NAT, carrier-grade NAT, VPNs, proxies, compromised devices and dynamic addressing can affect attribution.

## Evidence integrity and storage

The included JSONL sink writes append-only records with a SHA-256 hash chain and fsync. It verifies the existing chain before accepting new records. This is tamper-evident relative to a separately trusted/anchored chain head; it is not tamper-proof if an attacker can rewrite the entire file and its chain.

Before production use:
1. Configure encrypted, access-controlled durable storage or a managed append-only log service.
2. Restrict write access to the API service and read/export access to authorised incident responders.
3. Anchor the latest chain hash in an independent security account/service.
4. Configure backup, retention, monitoring, clock synchronisation and restore testing.
5. Add a documented legal/privacy retention policy and incident export/review workflow.
6. Verify the hosting platform's proxy behaviour and set trusted proxy CIDRs explicitly.

## Integration example

Wrap the deployed ASGI API at its application entry point:

```python
from security.ip_evidence import (
    JsonlEvidenceSink,
    NeonShieldEvidenceMiddleware,
    RequestEvidenceRecorder,
)

recorder = RequestEvidenceRecorder(
    JsonlEvidenceSink("/var/lib/neon-shield/evidence/events.jsonl"),
    destination_domain="api.your-real-domain.example",
    trusted_proxy_cidrs=(),  # Populate only with verified proxy CIDRs.
)
app = NeonShieldEvidenceMiddleware(app, recorder)
```

The example path and hostname are placeholders. The middleware is not active until the real deployed ASGI API is wrapped and the storage/proxy configuration is verified. Do not use a local file sink as the only production evidence store.

## Verification

Run `python -m unittest tests.test_ip_evidence` and the full repository test suite. Then test in a staging environment behind the actual reverse proxy, including spoofed X-Forwarded-For headers, 401/403/429 responses, storage failure, chain tampering and restart recovery.
