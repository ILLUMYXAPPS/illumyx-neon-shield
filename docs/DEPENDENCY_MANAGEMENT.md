# Dependency Management Policy

Neon Shield has separate Python desktop and Flutter mobile dependency graphs. Dependency changes must remain reviewable and reproducible; automated updates do not authorize automatic merging or release.

## Current controls

- Dependabot checks GitHub Actions, pip, and pub dependencies weekly.
- The security gate runs `pip-audit` against `requirements.txt`; this checks known Python package advisories, not application code or every native/system library.
- Python runtime dependency pinning is proposed separately in PR #138. Do not treat the pin as active on `main` until that PR is reviewed and merged.
- The mobile manifest is `mobile/pubspec.yaml`. A committed `mobile/pubspec.lock` was not present on the audited default branch; generate it with the project's supported Flutter SDK, review the resolved versions, and commit it before calling mobile dependency resolution reproducible.

## Required workflow for dependency changes

1. Prefer narrow, reviewed upgrades. Review release notes, supported Python/Dart/Flutter versions, platform compatibility, and transitive dependency changes.
2. Run the repository's CI, tests, linters, and applicable security scans against the exact pull-request commit.
3. Regenerate lockfiles with the documented toolchain. Do not hand-author lockfile contents or claim reproducibility without a real resolver run.
4. Investigate vulnerability findings and document any exception with an owner, rationale, and expiry/review date. Do not silently suppress findings.
5. Keep GitHub Actions pinned to reviewed immutable commit SHAs where required by repository policy; verify the upstream action and release before changing a pin.
6. Never auto-merge dependency updates or bypass required human reviews, branch protection, signed commits, CodeQL, or conversation resolution.
7. Before a release, verify clean installs from the committed manifests/lockfiles and retain the CI evidence for the exact release commit.

## Release acceptance checklist

- [ ] Python runtime dependencies are pinned to reviewed versions; the complete dependency-resolution strategy is documented.
- [ ] Flutter lockfile is generated by the supported Flutter/Dart toolchain and committed.
- [ ] Python dependency audit passes on the exact commit.
- [ ] Flutter dependency resolution, analysis, and tests pass on the exact commit.
- [ ] Dependabot changes and security alerts have been reviewed, not merely auto-closed.
- [ ] Any unresolved vulnerability or exception has documented risk acceptance and a follow-up date.
- [ ] Required independent reviews and repository protection rules remain satisfied.

## Scope and limitations

A clean dependency audit only indicates that the audit tool found no known advisories in the packages it successfully resolved at that time. It does not prove the software is secure, detect all malicious packages, audit every operating-system library, or replace code review and device/production testing.
